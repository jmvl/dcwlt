# Phase 5.5: Cryptographic QR Payment - Context

**Gathered:** 2026-03-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Reverse the payment flow: Client PWA generates a dynamic cryptographic QR code, Merchant scans to receive payment. This changes the direction from "merchant displays QR, client scans" to "client displays QR, merchant scans". No new payment capabilities — just flow reversal with cryptographic security.

</domain>

<decisions>
## Implementation Decisions

### QR Payload & Security

- **QR Contents:** User ID + time-based derived key (TOTP-like, changes every minute) + HMAC signature
- **Key Derivation:** Convex user ID + server-side secret (wallet key not accessible in PWA)
- **QR Format:** URL scheme: `dcwlt://pay?u=USER_ID&k=TIME_KEY&s=HMAC_SIGNATURE`
- **Expiry:** 5 minutes validity window
- **Refresh:** Auto-refresh with fade animation when QR expires
- **Clock Sync:** Allow ±2 minutes skew between client and server
- **Offline Generation:** Allow offline QR generation using cached seed + device time
- **Verification:** Server-side atomic validation (signature + timestamp + balance)
- **Rate Limiting:** 10 QR generations per minute per user
- **Multi-Scan:** Allow multiple scans within validity window (same QR can pay multiple times)
- **Error Messages:** Detailed errors (expired QR, invalid signature, insufficient balance)

### Client QR Display

- **Trigger:** Button-triggered from dashboard ("Show Payment QR")
- **Location:** Full-screen modal with centered QR
- **Brightness:** Auto-max screen brightness when QR displayed
- **Info Display:** QR code + countdown timer (no user avatar needed)
- **Countdown Format:** Minutes:seconds (e.g., "4:32 remaining")
- **Refresh Transition:** Fade out/in animation when auto-refreshing

### Merchant Scanner UX

- **Scan Entry:** "Scan Customer" button in merchant terminal
- **Camera Interface:** Full-screen camera with scan overlay
- **Payment Flow:** Scan → Instant payment (amount already in merchant cart)
- **Empty Cart:** Require items in cart before scanning (enforced by UI)
- **Post-Payment:** Success screen with amount + customer info, auto-dismiss after 3 seconds
- **Scan Feedback:** Sound + vibration + toast notification
- **Error Display:** Detailed errors with suggested actions (e.g., "Ask customer to refresh QR")

### Payment Verification

- **Verification Method:** Atomic Convex mutation (validate + transfer in single transaction)
- **Insufficient Balance:** Decline with clear error message, no partial payments
- **Confirmation:**
  - Merchant: On-screen success message
  - Customer: Toast notification + real-time balance update
- **Atomicity:** Convex transaction wrapping entire payment operation
- **Timeout:** 10 second payment processing timeout
- **Receipts:** Stored in transactions table, viewable in history

### Claude's Discretion

- Exact QR code visual styling and size
- Animation timing for fade transitions
- Error toast positioning and duration
- Success screen layout details
- Loading states during payment processing

</decisions>

<specifics>
## Specific Ideas

- "User ID with a derived key that changes every minute" — TOTP-like approach for time-based security
- Merchant already has the amount from their cart/cash register — no amount entry needed at scan time
- "Just show QR and paid" — minimal friction for customer
- Flow mirrors real-world: customer shows "card" (QR), merchant "swipes" (scans)

</specifics>

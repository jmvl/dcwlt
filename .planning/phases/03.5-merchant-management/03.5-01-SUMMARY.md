## Decisions Made

1. **Mock wallet generation for POC**
   - Plan specified "Privy wallet auto-generation" but didn't provide API details
   - Implemented deterministic mock wallet generation from email hash
   - Uses base58 encoding to simulate Solana address format (44 chars)
   - **Rationale:** Enables POC testing without Privy embedded wallet API, easy to replace with real Privy call in production

2. **Email validation in both client and server**
   - Client-side regex validation for immediate feedback
   - Server-side validation in mutation for security
   - Duplicate check before insertion to prevent race conditions
   - **Rationale:** Defense in depth, better UX with immediate feedback, security with server validation

3. **No wallet display in registration flow**
   - Merchants never see their wallet address during registration
   - Success message only confirms "Application submitted"
   - Wallet address stored in database but hidden from UI
   - **Rationale:** Matches Phase 2 pattern (users don't see wallets), reduces cognitive load
